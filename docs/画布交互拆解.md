## 1. 坐标系：为什么是零翻转

这一节单独成节，因为它会被后续所有 UI 代码引用，且**误读代价是"画面上下颠倒"——项目里最难被自动测试发现的 bug**。

### 1.1 完整因果链

```
AppKit 默认 Y 向上（原点左下）
        ↓ 所以 Mac 版必须显式翻转
EditorCanvas.swift:670   override var isFlipped: Bool { true }
        ↓ 视图坐标系变成 Y 向下（左上原点）
CanvasViewport.swift:25-33  纯线性变换，无 Y 取反
        ↓ 文档坐标与视图坐标同向
文档坐标 = 左上原点、Y 向下（与 .comp manifest 一致，零翻转）

Avalonia 默认就是 Y 向上吗？→ 不是。Avalonia/WPF 默认 Y 向下，与文档坐标天然一致。
        ↓
移植时的等价物 = 什么都不做
```

### 1.2 逐条证据

**① `EditorCanvas.swift:670`**
```swift
override var isFlipped: Bool { true }
```
AppKit 的 `NSView` 默认 `isFlipped == false`（Y 向上）。这一行是**整个坐标系的地基**。

**② 四个覆盖层全部同样翻转**（说明这是全局约定，不是局部补丁）：

| 文件:行号 | 代码 |
|---|---|
| `CanvasLinesOverlay.swift:8` | `override var isFlipped: Bool { true }` |
| `TransformOverlay.swift:61` | `override var isFlipped: Bool { true }` |
| `BrushCursorOverlay.swift:15` | `override var isFlipped: Bool { true }` |
| `SampleRingOverlay.swift:7` | `override var isFlipped: Bool { true }` |
| `CanvasRulers.swift:55` | `override var isFlipped: Bool { true }` |

**③ `CanvasViewport.swift:25-33` 因此不需要取反**
```swift
func documentPoint(from point: CGPoint, documentSize: CGSize) -> CGPoint {
    let origin = documentRect(documentSize).origin
    return CGPoint(x: (point.x - origin.x) / pointsPerPixel,
                   y: (point.y - origin.y) / pointsPerPixel)   // ← 没有 -y
}
func viewPoint(from point: CGPoint, documentSize: CGSize) -> CGPoint {
    let origin = documentRect(documentSize).origin
    return CGPoint(x: origin.x + point.x * pointsPerPixel,
                   y: origin.y + point.y * pointsPerPixel)   // ← 没有 -y
}
```

**④ 契约层与之一致**：`Geometry.cs` 的 `DocCoord.FromView` / `ToView` 同样是纯线性，无 Y 取反，且被 `tests/Compositor.Core.Tests/Contract/GeometryTests.cs:30` 锁死。

### 1.3 移植纪律

| 规则 | 说明 |
|---|---|
| ✅ **什么都不写** | Avalonia 的 `Control` 坐标系本就是 Y 向下（左上原点） |
| ❌ 禁止 `ScaleTransform(1, -1)` | 会把画面翻回来，等于自找颠倒 |
| ❌ 禁止任何 `height - y` / `(canvasH - y)` | 同上 |
| ✅ 业务代码一律用 `DocPoint` | `ViewPoint` 只能活在 UI 边界 |
| ✅ 读 `.comp` manifest 数值**零翻转** | 契约 `LayerTransform.Origin` 就是左上角（`附录A:318`） |

> **⚠️ 铁律 1 容易被误读的地方**：字面上"零翻转 = 什么都不做"是对的，
> 但如果因此**找不到 Mac 版那个 `isFlipped` 去哪了**，就会怀疑"是不是漏翻了"，
> 从而**多写一个翻转**。答案就是：AppKit 默认 Y 向上所以要翻，Avalonia 默认 Y 向下所以不用翻。

### 1.4 唯一允许出现的局部 Y 翻转（易误抄）

`BrushCursorOverlay.swift:46-48`：
```swift
// The view is flipped; images draw bottom-up.
context.translateBy(x: circle.minX, y: circle.maxY)
context.scaleBy(x: 1, y: -1)
```

**这不是坐标系翻转**，是**绘制位图**时的局部补偿：CGContext 画图像约定原点在左下，
而视图已翻转，所以画图前把这一小块单独翻回来。作用范围仅限这一次 `context.draw` 调用。

同理 `EditorCanvas.swift:906-909` 用 `beginTransparencyLayer` 包裹，
`TransformOverlay.swift:156-158` 在 `traceOutline` 里对**离屏 mask 位图**做 `scaleBy(x: fill, y: -fill)`
（注释："Top-left origin, so a mask row is a document row"）——同样是位图操作，与文档坐标无关。

**SkiaSharp 无需任何等价处理**：Skia 的画布本来就是 Y 向下、图像从左上角绘制。
照抄这两处反而会画反。

### 3.4 ⚠️ `CanvasLinesOverlay.swift` 是壳，**不要实现**

**真正的实现在 `EditorCanvas.swift:1398` 的 `drawLines`**，通过 `EditorCanvas.swift:662` 注入：
```swift
lines.drawLines = { [weak self] dirtyRect in self?.drawLines(in: dirtyRect) }
```

**它存在的唯一理由**（注释见 `CanvasLinesOverlay.swift:3-5`）：
让线条画在**自己的一层**上，这样无论底下是 GPU 还是 Core Graphics 画的，
线条外观一致，也避免重绘时把下面的棋盘格和图层合成一起重画。

`EditorCanvas.swift:653-660` 还给四个覆盖层都设了 `wantsLayer = true`，
注释（`657-659`）解释了原因：不设层的话，**每画一次透明覆盖层**（裁剪/变换拖动、蚂蚁线每跳一格、
光标移动）都会让 AppKit 重画底下的画布。

> **移植提示**：Avalonia 里对应的是"覆盖层是独立 Control，叠在画布 Control 之上"，
> 而不是去实现这个壳。**实现 12 行壳本身没有意义**——它的逻辑已经在画布那一侧。

### 3.5 蚂蚁线的性能分级（`TransformOverlay.swift:92-177`）

**这段是 Mac 版踩过性能坑后的产物，注释写得很直白，不应被简化掉。**

- 问题（`94-97` 注释）：魔棒轮廓在复杂图上可达**几十万条边**（每像素一步）。
  缩小后挤成几个屏幕像素，每次重绘要几秒，**曾经卡死应用**。
- 方案（`96-97` 注释）：缩放 <1:1 时，复杂轮廓改用**屏幕分辨率的描边**：

- 阈值（`100`）：`fullDetailLimit = 20_000` 个路径元素以内**永远全精度绘制**
  （选框和套索必须精确）。
- `antsOutline:110-139`：路径变化时取消旧任务；`step` 按 2 的幂取整，避免缩放时每帧重描。
- `125-136`：新 `step` 未描完前，**旧的继续顶替**（注释 `137`："a little coarse or fine for a moment, never slow"）。
- `traceOutline:143-177`：离屏 mask 填充上限约 4000 万像素（`148`），

## 5. 契约偏差清单

> 只记录，**不擅自改契约**。需变更由总项目管理在契约评审时处理。

### 5.1 🔴 `Viewport` 存的是派生值，不是二因子分解

> **v1.2 裁决澄清**（总项目管理 2026-10-07）。本文初版把这条写成"契约缺 `backingScale` 字段"，**表述不准确，已更正**。

字段并不缺失。对照关系：

| Mac `CanvasViewport.swift` | 契约 v1.1 `Viewport(OriginX, OriginY, PointsPerPixel, Scale)` |
|---|---|
| `backingScale`（`:7`） | **`= Scale`** |
| `pointsPerPixel = zoom / backingScale`（`:15`，**派生**） | 存的是这个**派生结果** |
| `zoom`（`:8` `private(set)`，range `0.001...32` = `:11`） | 无（派生） |
| `viewSize`（`:6`） | 无 |
| `pan`（`:9`） | 拆成 `OriginX` / `OriginY` |
| `followsFit`（`:10`） | 无 |

**真实差异**：`PointsPerPixel` 是 `zoom / backingScale` 的**快照**，不是因子分解。
`backingScale` 一变（拖到不同 DPI 显示器），仅凭契约的 `Viewport` **无法重算** `PointsPerPixel`。

**证据链**（backingScale 的获取与消费）：

- `EditorCanvas.swift:852` 用 `convertToBacking(CGSize(1,1)).width` 取得 backingScale
- `CanvasViewport.swift:47` `backingScale = max(1, newScale)`
- 消费点：`EditorCanvas.swift:913`（线宽 `1/backingScale`）、`1421`（像素网格线宽）、
  `TransformOverlay.swift:200`/`244`（线宽）、`121`（蚂蚁线 scale）

**处理**：`Viewport` 是权威类型；`Scale` 即 DPI 系数。计算 `fit` / `resize` / `setZoom`
时把 `zoom` 显式传参，在 UI 层做除法。**不要改契约。**

### 5.2 UI 层辅助方法的归属

留在 UI 层 `ViewportMath`，出处已标注在其 XML 注释的行号里。

### 5.3 `Viewport.Scale` 与 `PointsPerPixel` 语义重叠

契约测试 `GeometryTests.cs:173-180` 专门锁住了这一点：
`Scale` 是**给 UI 渲染用的重复表示**，若误当除数会让同一份 viewport 在不同调用点算出不同坐标，
且因为"两处都能跑"极难发现。

**移植纪律**：`Scale` 只用于渲染，坐标换算**只用** `PointsPerPixel`。
